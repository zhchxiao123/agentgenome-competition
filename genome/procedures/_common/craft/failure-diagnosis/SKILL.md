# failure-diagnosis

拿到失败报告先诊断,再动手。**顺序不能反。**

## 为什么这条值得单独成一份手艺

直接改代码撞运气的失败模式非常一致:第一轮改了一个看起来相关的地方,测试换了个错法;
第二轮再改,又换一个错法;第三轮撞上修复轮次上限,任务升级人工。而人接手后往往发现
真正的原因在第一轮报告的第二行里写着。

**每一轮都是全新的 Job。** 你这一轮不诊断清楚,下一轮的你拿到的还是同样一份报告。

## 四步

1. **读断言差异,不是读日志。** 失败报告里结构化条目在前、`log_tail` 在后,这个顺序
   是故意的。先看 `expected` 与 `actual` 差在哪 —— 那是最浓缩的信息。
2. **定位到行。** 报告里有 `file` 与 `line`。打开那一行,连同它的调用方一起看。
3. **写出假设,再验证。** 假设要具体到"如果我的判断对,那么改 X 之后 Y 应该变成 Z"。
   写不出这句话说明你还没诊断清楚。
4. **只改假设指向的地方。** 一轮只验证一个假设。同时改三处的话,测试变绿了你也不知道
   是哪一处起了作用 —— 而另外两处可能正在制造下一个 bug。

## 有多轮失败报告时

上下文包里会有历史各轮的报告,**失败报告置顶**。先对比:

- 同一个用例一直挂 → 你一直没找到真正的原因,换思路而不是换写法。
- 挂的用例变了 → 上一轮改坏了别的东西,先看回归对比那一段。
- 错误信息变了但用例没变 → 你在正确方向上,继续。

## 反例

- ❌ 看到报错就去搜索引擎式地改一个常见写法 —— 这是在赌,不是在修。
- ❌ 通篇读 `log_tail` 然后凭印象下结论 —— 那 200 行里绝大部分是噪声。
- ❌ "先加个 try/except 让它过去" —— 门禁会绿,问题会留在生产。
- ❌ 一轮同时改五个文件 —— 下一轮报告变了你也无法归因。
- ✅ 读断言 → 打开出错那一行 → 写下"我认为是 A 导致的,因为 B" → 只改 A → 跑测试。

## 自检

- [ ] 我能用一句话说出这次失败的**原因**,不只是现象
- [ ] 我这一轮只验证了一个假设
- [ ] 如果有历史轮次,我对比过它们的差异
- [ ] 我没有为了让测试变绿而放宽断言或吞掉异常
