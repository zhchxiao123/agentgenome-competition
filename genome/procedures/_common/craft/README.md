# 手艺写作规范

手艺(Craft Skill)教员工**这类活怎么干得好**。它不是文档,是一份能被照着执行的清单。

## 五条硬规矩

1. **一份手艺只讲一门手艺。** 「怎么勘察代码库」和「怎么写知识卡片」是两份,不是一份的两节。
   合在一起的后果是员工为了用其中一半而加载全部,预算白花在不相关的内容上。
2. **不超过 200 行。** 超了说明它其实是两份。校验会告警但不拒绝——行数是内容质量问题,
   不该让一份稍长的手艺把整个工序打挂。
3. **清单式,不是散文。** 能写成有序步骤的不要写成段落。员工是照着做,不是读完受启发。
4. **必须含反例。** 只说"该怎么做"的手艺没有判别力——员工分不清自己现在做的算不算数。
   写清楚"下面这样是错的,因为……"。
5. **不与契约重复。** 输入输出定义、产物 schema、触发条件都在 `procedure.yaml` 里。
   在手艺里再写一遍,两处必然发散,而发散之后没人知道哪份是对的。

## 结构建议

```markdown
# <手艺名>

<一句话:什么时候用它>

## 步骤
1. …
2. …

## 反例
- ❌ …  ← 为什么错
- ✅ …

## 自检
- [ ] …
```

## 它凭什么值得存在

**手艺要能被测出来有用。** 判据不是"读起来有道理",是挂与不挂这份手艺跑同一批任务,
修复轮次与门禁一次通过率有没有差别(见 `tests/drift/test_craft_ab.py`)。
一份测不出差别的手艺应该删掉,而不是留着占预算。
