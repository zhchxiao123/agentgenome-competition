# 反馈环不是依赖边:迭代由终止判据表达

执行拓扑要同时装下两类"回头":

- `generate → critique → refine → critique → …` 这种**精化环**(由批判驱动,收敛即停);
- 以及一张画错了的图上 `A → B → C → A` 这种**依赖成环**。

两者在朴素的图表示里长得一模一样(都是一条指回上游的边),但它们的正确处理**完全相反**:
前者要跑,后者要当场拒绝。

## 决定

1. **依赖图必须无环,环检测在派发前拒绝成环的图。** 拒绝发生在**加载那一刻,不是调度那一
   刻**(这条判断从被取代的子任务图继承):调度时才发现的症状是"任务提交之后什么都没发生"
   ——一个没有任何错误信息的静默死锁,排查极贵。
2. **迭代不走依赖边,走 `Termination`。** 模板上的终止判据说明这张图要跑几轮、什么条件
   算收敛、整个环最多花多少预算。于是环检测与迭代不再是同一个东西,前者可以无例外地严格。
3. **有环就必须有终止判据,反之亦然。** 没有终止判据的环是没有上限的花费(loop
   engineering 退化成 loop burning);而终止判据里**预算份额与轮次上限同样必要**:轮次
   封顶管得住次数,管不住单轮的花费,而"成本可归因"不等于"成本有上限"。
4. **精化轮次不消耗任务的修复轮次。** 修复轮次是**重试环**(由失败驱动,门禁说了算),
   精化是**批判环**(由评审驱动,环内说了算)。两个计数器混用的后果与既有的契约重试外环
   一样:悄悄绕过其中一条上限。

## 代价

模板里多了一个"必须成对出现"的约束(有环 ⇒ 有 `Termination`),它由模板作者而不是类型
系统保证——本期只有内置模板,作者是我们自己;等到 plan 产图那一天,这条要进图校验器。
