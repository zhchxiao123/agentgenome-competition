# 挂起复用崩溃恢复那条路,不新造恢复机制

派给人的 Job 以**工作日**计。执行模型此前是"一次 `advance` 调用内 await 一个 Job 跑完",
而执行池在两把锁里跑完整个 `run_job`。把一份人类作业放进这条路,会同时踩三个坑:一个协程挂
三天;占掉执行池的一个并发名额(而泳道的理由是"子进程既吃机器也吃 API 配额",人两样都不吃);
进程一重启,那一等就没了,恢复会重推一步、产物还不在,于是**再投一张待办**。

外部工作流引擎(Temporal 之类)卖的核心能力正是这一条:**durable execution**——一个执行单元
可以挂起数天、跨进程重启、由外部事件唤醒继续。

## 决定

**不引外部引擎,而是让 Job 可以挂起;挂起的恢复复用已有的崩溃恢复路径。**

1. `run_job` 投完待办**立刻返回**一个"挂起"的结果;两把锁随即释放。挂起不复用失败语义——
   失败会让状态机重试、升级、扣一轮修复轮次,而这三样对"人还没开始干"都是错的。
2. 编排器见到挂起就**原样返回,不抛任何状态机事件**:状态不动。这正是「待确认」的表示。
3. 任务上记一条"在等哪张待办";`can_advance` 因此返回否——那里已经有一条"结对进行中不该被推"
   的同款判断,服务端与编排器共用它。
4. **人交完活 = 产物已存在 = 崩溃恢复。** 提交把产物写进这次派发当初分配的那个产物槽,清掉
   标记,照常推一步——处理器的幂等约定会认出产物,走既有的重放路径抛出它本来就该抛的事件。

于是"继续"不依赖任何内存态,挂起三天、进程重启十次都不影响它。

## 代价

**两处幂等成了硬要求,而它们都没有类型系统兜底。**

- **投递幂等**:待办按 `(任务, 阶段, 节点, 轮次)` 唯一,待办 id 从这把键派生而不是随机的
  ——随机 id 意味着"这次派发对应哪张待办"要另存一份映射,而崩溃正好发生在写下那份映射之前。
- **节点级幂等**:人交完活之后整张图会被重走一遍,机器那几步不能再花一次钱,更不能再给人
  投一张待办(那会形成一个人的答复永远接不回来的死循环)。所以产物清单里记下"这个槽属于
  任务的第几轮",让"这一轮里这个节点已经产出过了"成为一个可判的事实。

**到期只能靠扫描问。** 没有协程在等,所以"三天没人接"这件事由外面定期来问——形状与调度那边
的到期检查同源,而扫描必须幂等(同一分钟连跑三次,提醒只发一次)。

**这条路对"等外部系统"的 Job 同样成立**(将来的外部审批、CI 回调):它们与人一样,是"活派
出去了,结果要等外面回来"。这是把它做成通用挂起而不是"人专用等待"的理由。
