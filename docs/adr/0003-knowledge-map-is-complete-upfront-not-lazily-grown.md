# 知识地图在初始化时一次建完,不随任务执行懒生成

分层知识地图(L0 根索引 / L1 模块地图 / L2 功能卡片)一度设计成「骨架优先、懒生成补全」:
初始化只为 git 热区生成 L2 卡片,其余 feature 标记 pending,等某个研发任务路由命中时再由
管道补生成。理由是冷启动成本——大型存量项目「读懂全库」很贵。

我们放弃了懒生成,改为**初始化必须产出完备的知识地图**。决定性的理由不是成本,是**懒生成会
让「系统对某个模块懂多少」变成任务历史的函数**:两个内容相同的需求,先提的那个拿到的上下文
比后提的差,而差在哪无法预测、无法测试。上下文包可离线复现(§5.4)只保证包本身可复现,
不保证知识覆盖是稳定的。地图是契约,不是缓存。

顺带发现懒生成与既有的 `knowledge-update` Procedure 重复:「代码变了,卡片要跟上」与「卡片本来
就缺,要补上」是同一件事,走同一条经过门禁与架构员工的路径即可,不需要第三条绕过门禁的
写入路径。

## Consequences

- **完备性靠不变式强制,不靠自觉**:loader 校验从单向(无孤儿卡片)改为双向,补上「L1 map
  里的每个 feature 条目,必须要么有卡片,要么有一条带理由的 `card: none` 声明」。
  「这里没知识」是缺口,「这里不需要知识」是一个被记录下来的判断——两者必须能区分开,否则
  为纯 CRUD 强凑卡片只会产出一堆永远 0 命中的水卡,反过来污染按 `hits` 做自然选择的机制。
- **初始化的成本画像从分钟级变成小时级**,因此知识初始化必须全异步:人工确认模块边界的闸门
  要能持久化、能隔天从 Web 回答,不能是同步的 CLI 交互。这两个决定是一体的,不能只采纳一半。
