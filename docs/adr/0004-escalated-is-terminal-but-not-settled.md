# `ESCALATED` 是终态,但不是「已了结」——所以有两个谓词,不是一个

`TaskState` 上有两个几乎一样的谓词:`terminal()` = {COMPLETED, ESCALATED, CANCELLED},
`settled()` = {COMPLETED, CANCELLED}。看起来像重复,不是。`terminal` 回答「状态机还会不会自动
迁移」,管迁移表(`decide`)、状态图、写任务报告、触发蒸馏;`settled` 回答「人还要不要看见它」,
只管列表查询。两者差的那一个 `ESCALATED` 恰恰是最需要人注意的状态。

合并它们不是假设,是这个仓库真实犯过的错:`GET /tasks` 与 `agctl task list` 都复用了调度队列的
`open_tasks()`(排除全部终态),于是任务一路走到升级人工之后就从所有列表里消失,而
`GET /tasks/{id}` 照常返回详情——症状看起来像「任务从来没提交成功」,没有任何界面能回答
「我提的任务哪去了」。修复是给列表加一个 `unsettled_tasks()` 查询;`open_tasks()` 语义一个字
不改,调度器继续用它。

## Considered Options

**让 `ESCALATED` 不再是终态,允许人工接管后回到流程**(收件箱语义)被否决。它要求:蒸馏管道从
「任务终结这一刻收集一次」改成可重入(`_pending_distill` 是单槽的,重入会重复蒸馏,而这是自进化
唯一的触发点);`Task` 新增字段记住升级前所处的状态(现在只有 `escalate_reason` 一段文本);
`TaskEvent` 引入第一类人发起的事件;还要处理「因预算耗尽升级的任务一点继续就立刻回弹」——预算
检查是横切规则,`tokens_used` 不变就一定再次升级。代价与「让升级人工的任务可见」这个目标不成
比例。

如果以后确实需要「人修好环境后再来一次」,倾向的做法是**建一个指向原任务的新任务**,而不是复活
已终结的那个:旧任务留作历史与蒸馏素材,代价只有一个可空字段,不碰状态机、蒸馏与事件词汇。
