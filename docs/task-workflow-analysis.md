# 需求、任务与人工处理流程分析

日期：2026-08-14
分支：`codex/task-workflow-analysis`

## 结论

当前系统的状态机主体是清楚的，但“机器停手以后由谁、在哪里、做什么”没有形成闭环。

截图中的任务处于 `ESCALATED`。它不是审批任务，因此不进入审批中心是正确的；问题在于任务中心只展示“需要人工”和一段原因，没有接管、重试、转派、关闭、打开冻结现场等动作。用户唯一可走的路径，是先理解“所属需求”编号，再跳到需求管理详情底部发起“再试一次”。这是隐藏能力，不是可操作流程。

更严重的是，`ESCALATED` 是任务终态但不是已了结状态。旧任务没有任何“人工事项已处理”的记录，所以即使同一需求的后续尝试已经交付，旧任务仍永久留在任务中心并计入“需我处理/异常”。系统能表达“机器停止了”，不能表达“人已经处理完了”。

建议保留研发任务不可复活、`ESCALATED` 仍为终态的决定；在任务状态机之外增加一等的“人工介入事项”，专门承载认领、处理方式、后继尝试和了结状态。审批、人工执行待办、人工介入必须继续分开。

## 一、当前领域对象与实际流程

### 1. 需求与任务

- 需求（Requirement）是长期容器，一条需求可以有多次研发任务尝试。
- 研发任务（Task）是一次性的执行尝试。失败后不复活旧任务，而是在同一需求下创建新任务。
- `Task.requirement` 是开工时的需求快照；需求当前文本后续可修改，不回写旧任务。
- 需求状态由尝试链推导：
  - 有完成尝试：`delivered`
  - 有非终态尝试：`in_progress`
  - 全部尝试为 `ESCALATED`/`CANCELLED` 或尚无尝试：`queued`
  - 人工搁置优先：`parked`

这个建模方向是合理的，它避免了“重启旧任务”造成事件、成本、产物和蒸馏重复。

### 2. 研发任务状态机

主干流程为：

```text
CREATED
  → DEVELOPING
  → UNIT_TESTING
  → [INTEGRATION_TESTING]
  → READY_TO_COMMIT
  → REVIEWING（高风险）/ MERGING（低风险）
  → MERGING
  → COMPLETED
```

回路为：

- 单测失败、集测失败、提交前检查失败：可恢复且还有轮次时回到 `DEVELOPING`。
- 审批驳回、合并冲突：回到 `DEVELOPING`。
- 需求解析失败：最多重试一次。

升级人工的来源包括：

- 需求解析重试耗尽。
- 单测、集测、提交前检查不可恢复，或修复轮次耗尽。
- token 预算耗尽或不足以运行下一 Job。
- 员工归属冲突、空授权范围、执行拓扑不可运行。
- 连续迁移拒绝达到上限。
- 人工执行待办长期无人处理并走完提醒/改派策略。

上述路径最终进入 `ESCALATED`，冻结分支与工作区、固化审计包、触发经验回流。`ESCALATED` 是终态，机器不会再迁移。

### 3. 系统里其实有四种“等人”

| 场景 | 含义 | 当前入口 | 人的动作 | 是否完整 |
|---|---|---|---|---|
| `REVIEWING` | 审批整个任务产出 | 审批中心 | 通过或驳回 | 基本完整 |
| Human Job / `pending_todo_id` | 一份工作交给人执行 | 工作台“我的待办” | 提交契约化产物 | 基本完整 |
| `AWAITING_CONFIRMATION` | 健康流程中的计划内确认 | 基因组任务详情 | 回答边界问题 | 基本完整 |
| `ESCALATED` | 自动尝试失败，需要人处置异常 | 任务中心 | 当前没有动作 | **断裂** |

因此，把截图中的任务塞进审批中心会制造新的语义错误。审批回答“这份产出可否通过”；升级人工回答“这次自动尝试失败后怎么办”。两者需要不同权限、证据和结果。

## 二、从提交到结束的界面闭环检查

### 1. 需求提交

当前行为：`POST /tasks` 先创建需求，再创建第一次任务尝试；提交成功后跳到需求详情。

问题：

1. 创建需求和创建任务不是同一个数据库事务。第二步失败会留下没有尝试的孤立需求。
2. 名称“提交需求”与接口 `POST /tasks` 不一致，重试也复用这个接口，服务端难以对“新需求”和“新尝试”实施不同约束。
3. 提交后任务只是 `CREATED`，不会由服务端持续自动推进。Web 的 `/run` 一次只推进一个状态，用户需要在多个阶段重复点击“继续推进”；页面文案却称为“自动流程”。

建议：

- 由一个需求入口模块在单事务内完成“需求 + 首次尝试”。
- 新尝试使用显式接口 `POST /requirements/{id}/attempts`，而不是让调用方在 `POST /tasks` 中偷带 `requirement_id`。
- 明确运行策略：若产品目标是自动执行，服务端应有持久调度驱动到外部闸门或终态；若目标是逐步人工驱动，界面不要称为自动流程。

### 2. 需求管理

当前能力：看状态、看尝试链、累计 token、再试一次、搁置/恢复。

问题：

1. “再试一次”在任何需求状态都显示，包括已有进行中尝试、已搁置、已交付。
2. 后端没有限制同一需求同时存在多个活跃尝试，重复点击或多人操作可产生并行尝试。
3. 搁置需求不会取消正在运行的任务，这是领域文档中的刻意决定，但界面没有提示其后果。
4. 发起新尝试后只刷新需求详情，不直接打开新任务，用户还要从尝试链寻找刚创建的任务。

建议约束：

- 默认同一需求最多一个未终态尝试；并行尝试必须是显式的高级动作。
- `parked` 时先恢复才能创建尝试。
- `delivered` 时动作名改为“发起后续改动”，避免把已交付误称为重试。
- 创建成功后展示并打开新任务，且把旧介入事项标为已处置。

### 3. 任务中心

当前能力：未了结任务列表/看板、状态、原因、执行过程、产物、事件、所属需求。

做对的部分：

- 列表使用 `unsettled_tasks()`，不会像旧实现一样把 `ESCALATED` 完全隐藏。
- 区分待审批、待确认和异常升级。
- `can_run` 由服务端计算，前端不复制状态机规则。

主要断点：

1. `ESCALATED` 详情隐藏全部头部动作。终态会隐藏推进、更多菜单和取消；页面只有“需要人工处理”文案。
2. 没有人工负责人、认领时间、处理 SLA、处理备注、转派与通知状态。
3. 虽然状态机执行了 `FREEZE`，界面不展示冻结分支/工作区的可用入口，也没有“复制路径/打开现场”。
4. `escalate_reason` 只有自由文本，没有原因码、失败阶段、推荐动作、相关证据指针。
5. 任务无法被人工标记为已处置，导致异常队列永久增长。
6. 后续尝试交付时，旧任务只显示“该需求已由后续尝试交付”，但仍计入“需我处理/异常”。
7. 截图中的“CREATED 态修复轮次达到上限 3”是错误原因：实际是需求解析两次都触发单 Job token 上限，耗尽的是 `plan_retries=1`；卡片上的 `fix_rounds=0` 反而是正确的。状态机的通用升级原因混用了需求解析重试上限与开发修复轮次上限。
8. 人工发起的基因组任务进入 `FAILED` 后也被计入“需我处理/异常”，但详情同样只有“需要诊断”和失败原因，没有重试、关闭或新建后继任务动作；它与研发任务的 `ESCALATED` 是同一种“能报警、不能处理”的断点。

### 4. 审批中心

当前只列 `REVIEWING`，这是正确的。

仍需补强：

- 工作台和侧栏的待审批数按所有 `REVIEWING` 计算，不按当前用户可审批范围过滤。
- `actor` 输入框只是临时身份来源；正式身份启用前容易出现“看得到但无权操作”。
- 审批驳回与合并冲突都无修复轮次上限守卫，理论上可以无限回到开发态。若这是有意允许人工继续，应在状态机文档里明确“人工决定可突破自动轮次上限”；否则应统一进入人工处置。

## 三、截图问题的直接根因

截图对应的路径是：

```text
任务在 CREATED 阶段第一次需求解析失败
→ 按 plan_retries 规则重试一次
→ 第二次需求解析仍失败
→ Orchestrator 直接把任务改为 ESCALATED
→ 任务成为机器终态
→ TaskDetailPanel 因终态隐藏所有动作
→ ApprovalCenter 只收 REVIEWING，因此为空
→ 用户看到“需要人工”，但系统没有给出处理入口
```

对运行实例的事件日志核对后，这个具体任务的实际路径可以进一步收窄：

```text
requirement-analysis 第一次运行
→ 单 Job token 上限 200,000，实际 207,720，failure_kind=budget
→ PLAN_FAILED，任务仍为 CREATED
→ requirement-analysis 第二次运行
→ 实际 208,337 tokens，再次 failure_kind=budget
→ PLAN_FAILED 且需求解析重试耗尽
→ ESCALATED
```

所以截图里的原因文字本身就是错误的：它应该表达“需求解析重试上限 1 已耗尽，最近两次均为单 Job token 超限”，却被通用 `_escalation_reason()` 写成了“修复轮次上限 3”。这里混用了 `MAX_PLAN_RETRIES` 与 `max_fix_rounds`；界面显示 `fix_rounds=0` 是正确的，因为任务从未进入开发修复循环。

这条路径同时暴露三个设计缺口：

- 状态只描述机器，不描述人工处置。
- 原因只有文本，没有动作协议。
- 任务详情没有按状态返回可执行动作。

## 四、推荐目标模型

### 1. 不复活 `ESCALATED` 任务

保留以下不变量：

- `ESCALATED` 仍是任务终态。
- 旧任务的事件、成本、产物、审计包保持不变。
- 重新执行创建同一需求下的新任务。
- 不能把人改动偷偷记回已终结任务，避免任务报告与蒸馏重复。

### 2. 新增“人工介入事项”模块

人工介入事项（Intervention）与任务 1:1 或 1:N 关联，状态建议为：

```text
OPEN → CLAIMED → RESOLVED
                 ↘ CANCELLED
```

关键字段：

- `id`、`task_id`、`requirement_id`
- `reason_code`：`plan_invalid`、`environment`、`budget_exhausted`、`fix_exhausted`、`scope`、`topology`、`todo_expired`、`unknown`
- `reason_detail`、`failed_stage`
- `recommended_actions`
- `assignee`、`claimed_at`、`due_at`
- `resolution`：`retry_created`、`fixed_outside`、`requirement_parked`、`duplicate`、`accepted_failure`
- `resolution_note`、`successor_task_id`、`resolved_at`

模块对调用方只暴露少量接口：

```text
open_for_escalation(task, reason)
claim(intervention, actor)
resolve(intervention, resolution, note, successor_task_id?)
list_open(actor?, workspace?)
```

所有升级入口共用 `open_for_escalation`，所有页面共用服务端返回的可用动作，避免每个调用方重新猜规则。

### 3. “终态”与“已了结”的新判据

- 任务终态仍由 `TaskState.terminal()` 判断。
- 人工是否还要看，不再只由 `TaskState.settled()` 判断。
- `ESCALATED + intervention OPEN/CLAIMED`：未了结，进入人工队列。
- `ESCALATED + intervention RESOLVED/CANCELLED`：已了结，只在历史和需求尝试链中出现。

这样可以解决“后续尝试已交付，旧任务仍永久报警”的问题，而不需要复活旧任务。

### 4. 服务端返回动作，不让页面推导

任务详情建议增加：

```json
{
  "attention": {
    "kind": "intervention",
    "status": "open",
    "assignee": null,
    "reason_code": "plan_invalid",
    "recommended_actions": ["edit_requirement_and_retry", "park_requirement"]
  },
  "available_actions": [
    {"id": "claim", "label": "认领处理"},
    {"id": "retry", "label": "修改需求并新建尝试", "primary": true},
    {"id": "park", "label": "搁置需求"}
  ]
}
```

动作权限、状态条件和幂等性全部由服务端裁决；前端只负责呈现。

## 五、推荐界面流程

### 工作台

保留三个独立区域：

1. 我的执行待办：Human Job，需要交付产物。
2. 待我审批：`REVIEWING`，需要裁决。
3. 异常待处理：开放的 Intervention，需要诊断和选择处置方式。

“已升级人工”数字应可点击，直接进入已按优先级、等待时间、负责人排序的异常队列。

### 任务中心详情

`ESCALATED` 时在顶部显示固定处置卡：

- 为什么停：结构化原因 + 人话说明。
- 停在哪：失败阶段、最后一次有效产物、最近错误。
- 现场在哪：分支、工作树、审计包、失败报告。
- 谁在处理：未认领/负责人/已等待多久。
- 下一步：服务端返回的主操作与次操作。

按原因选择主操作：

- 需求/计划问题：`修改需求并新建尝试`。
- 环境/配置问题：`认领修复环境`，修好后 `新建尝试`。
- 修复轮次耗尽：`打开冻结现场` 或 `创建人工开发尝试`。
- 预算耗尽：`调整预算并新建尝试`，不能直接恢复旧任务。
- 不再处理：`搁置需求` 或 `接受失败并关闭`。

### 需求管理

需求详情继续承载长期视角；任务详情承载当前异常处置。两处可以共用“新建尝试”表单模块，但入口文案与默认上下文不同。

新尝试创建成功时：

1. 事务内创建新任务。
2. 将旧 Intervention 以 `retry_created` 了结，并记录 `successor_task_id`。
3. 跳到新任务详情。
4. 旧任务从开放异常队列移除，但仍在需求尝试链中可见。

## 六、实施优先级

### P0：先补真正的操作闭环

1. 新增 Intervention 存储、状态与事件。
2. 所有 `ESCALATED` 落地点统一创建 Intervention；为存量 `ESCALATED` 任务惰性补建开放事项。
3. 提供认领、了结、创建后继尝试的 REST 接口与 RBAC。
4. 任务详情增加异常处置卡；至少支持“修改需求并新建尝试”“搁置需求”“接受失败并关闭”。
5. 任务中心与工作台只统计开放 Intervention，不再直接统计全部 `ESCALATED`。
6. 新建尝试与了结旧 Intervention 必须在同一个事务或具有可重放的幂等键。

### P1：补诊断质量与可操作现场

1. 把 `escalate_reason` 升级为原因码 + 详情 + 证据指针。
2. 展示/复制冻结分支、工作树、失败报告和审计包路径。
3. 增加负责人、转派、SLA、提醒与通知。
4. 拆分 `fix_rounds`、`plan_retries`、`transition_refusals` 的展示语义。
5. 同一需求默认禁止多个活跃尝试。

### P2：统一自动化体验

1. 已选定“持续自动驱动”：用户只启动一次，服务端循环推进到外部闸门、挂起或终态。
2. 运行态与业务状态分开持久化，界面依据 `execution_status` 展示“执行中”“继续执行”。
3. 任务返回需要人工审批的闸门后，审批操作会自动恢复同一驱动循环。
4. 补全任务历史筛选，区分开放事项与全部历史任务。

## 七、验收测试

最小主流程应覆盖：

1. 提交需求 → 创建首次尝试 → 自动/手动推进规则与界面承诺一致。
2. 任务在 `CREATED`、测试、提交前检查、预算等不同来源升级时，都创建结构化 Intervention。
3. `ESCALATED` 任务详情必有至少一个可执行动作，不允许只显示“需要人工”。
4. 审批中心不出现 `ESCALATED`；异常队列不出现 `REVIEWING` 或 Human Job。
5. 从异常详情修改需求并创建新尝试 → 新任务挂在同一需求 → 旧事项已了结 → 旧任务不再计入“需我处理”。
6. 后继任务完成 → 需求为已交付 → 旧任务仍保留完整历史与“由哪个后继任务处理”的链接。
7. 双击“新建尝试”或请求重放不会创建两个任务。
8. 已搁置需求不能直接创建尝试；已有活跃尝试时默认拒绝再建一个。
9. 不同角色只看到和执行自己有权进行的动作，服务端直接调用同样拒绝越权。
10. 存量 `ESCALATED` 任务升级后能进入开放事项队列，不丢失、不重复。

## 八、已验证的证据

- `TaskState` 明确把 `ESCALATED` 定义为终态，但从 `settled` 中排除。
- `GET /tasks` 使用 `unsettled_tasks()`，因此所有 `ESCALATED` 会持续返回。
- `TaskDetailPanel` 对终态隐藏推进和更多菜单，`ESCALATED` 没有专属动作。
- `ApprovalCenter` 只筛选 `REVIEWING`。
- `Requirements` 页面确实提供“再试一次”，调用 `POST /tasks` 并携带 `requirement_id`。
- 控制台 P0 PRD 明确要求任务详情有“取消/重试/接管”，当前接管故事未实现。
- 隔离 Python harness 已验证：同一需求的后继任务 `COMPLETED` 后，需求状态为 `delivered`，旧 `ESCALATED` 任务仍由 `unsettled_tasks()` 返回。
- 对用户启动的真实前后端做了只读浏览器核对：工作台显示 1 个“已升级人工”，任务详情没有任何操作；需求详情存在隐藏的“再试一次”；审批中心为空；三个由人发起且失败的基因组任务同样只有诊断信息、没有处置动作。
- 真实任务 `ag-20260814-002` 的日志证明两次 `requirement-analysis` 都因 200,000 的单 Job token 上限失败（207,720 与 208,337），最终却错误展示为“修复轮次上限 3”。
- 状态机与需求推导的 12 个定向单元测试通过；两个 REST 端到端用例被示例仓内不可复制的 `.venv` 符号链接阻塞。
- 前端定向测试被本地缺失 `@rollup/rollup-darwin-arm64` 阻塞；测试源码当前明确断言升级任务不提供继续执行入口。

## 九、本次实施结果

- `TaskDriver` 负责连续驱动，`Orchestrator` 仍只处理单步状态迁移；两者职责分离。
- 点击一次“开始执行”后，任务会自动推进；按钮和列表立即投影为“执行中”。
- 需求解析失败会消耗 `plan_retries`，界面显示“重试需求解析”，不再错用开发修复轮次。
- 进程中断后服务端投影为 `interrupted`，界面显示“继续执行”，避免假死的“执行中”。
- Token 仍完整计量，但默认不作为 Job 中止或任务升级的业务门禁；后续可通过 `budgets.enforce` 重新启用。
