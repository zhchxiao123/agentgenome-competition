# 双层提交拓扑

一个跨模块任务的变更落在两层。这份文档说明这套机制**保证什么**、**不保证什么**。

## 拓扑

```
任务 ag-20260901-001(跨 order/inventory 两模块)
├── 子仓层:code-1 上分支 task/ag-20260901-001 → PR#12(业务代码变更)
│          code-2 上分支 task/ag-20260901-001 → PR#7 (业务代码变更)
└── 顶层:  workspace 上分支 task/ag-20260901-001 → PR#33
            (内容 = code-1/code-2 子模块指针前移)
```

Workspace 是纯协作仓,它只存指向各业务仓某个 commit 的指针(gitlink)。
"这一组仓库的这一组版本是一起生效的"这件事,就由顶层的一个指针提交来表达。

## 合并顺序

顺序是固定的,而且它**不是实现细节**:

1. **全部子仓 PR 合并**,按依赖拓扑排序——被依赖方先合;
2. 顶层 Workspace 分支上把各子模块指针统一前移,生成一个只含 gitlink 变化的提交;
3. **最后合并顶层 Workspace PR**。

第 3 步是任务完成的原子提交点。

## 保证什么

**一致性。** 顶层 PR 合并之前,主 Workspace 的指针仍指向旧版本——此刻 `clone --recurse-submodules`
顶层仓,拿到的是一组一致的旧版本;合并之后拿到的是一组一致的新版本。**不存在"订单已经用
新接口、库存还没提供"的中间态可以被 clone 到。**

**原子回滚。** `git revert` 顶层的那一个指针提交,即回滚整个任务的组合状态。
子仓历史一行不改,不需要跨仓协调,不需要改写任何已发布的历史。

**可重放。** 整个流程幂等:已合并的 PR 再走一遍返回同一结果,指针前移是覆盖写,
重复开 PR 会返回已有的那个。崩溃后重放不会重复合并。

## 不保证什么

> **Git 平台不支持跨仓事务。这套顺序是在逼近原子语义,不是提供事务保证。**

如果第二个子仓 PR 在第一个合并之后失败了(冲突、门禁未过、权限),**第一个子仓的
改动已经在它的主干上了**。系统会立刻中止、不再前移顶层指针,并在
`SubmoduleMergeFailed.already_merged` 里报告哪些子仓已经合并——但那些子仓的主干上
确实短暂存在过一个孤立的改动。

不要让使用者以为这里有事务保证。真实的保证是:

- 顶层视角(也就是任何人 clone 顶层仓看到的)始终一致;
- 子仓视角在失败窗口里可能有孤立改动,需要人工处理。

### 缓解措施

**按依赖拓扑排序,被依赖方先合。** 中间态窗口是真实存在的,那就让窗口里的状态尽量安全:
先合被依赖方,窗口里是"新接口已提供、调用方还没用"——向后兼容的接口变更下这是可用状态。
反过来("调用方已用新接口、提供方还没上线")则必然是坏的。

排序依据是项目地图的 `depends_on`。地图缺失或依赖成环时退回到给定顺序——排序是优化,
不该成为失败点。

**把子仓合并放在同一个短时间窗内。** 顺序执行、不插入审批或人工步骤,把窗口压到最小。

## 未被碰过的子仓

一个任务通常只改部分模块。没有对应任务分支的子仓会被跳过,并记录在
`DualLayerResult.skipped` 里。

**跳过是显式记录的,不是静默的**——"这个模块本来就没改"和"开发员工忘了 push"在
系统看来长得一样,得让人能分辨。
